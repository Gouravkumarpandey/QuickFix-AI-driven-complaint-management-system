# Advanced support workflows

Open **Advanced setup** in the workspace sidebar. The ticket inbox also has **Table and bulk actions**; email tickets have **Format email reply** and scanned-file selection. Phone actions contain a browser phone and private call history.

This extension builds on the existing workspace and enterprise modules. It does not merge or deploy automatically, supply provider accounts, send live test calls, charge real customers, or certify exact Freshdesk parity.

## Configure and validate providers

### Mail

Set `GOOGLE_MAIL_CLIENT_ID/SECRET` or `MICROSOFT_MAIL_CLIENT_ID/SECRET`. Register the exact callback `<BACKEND_URL>/api/mail-oauth/callback`. Use **Advanced setup → Email** with an existing email connection. Set `IMAP_ALLOWED_HOSTS` to the approved provider host (`imap.gmail.com` or `outlook.office365.com`). Preserve the API/worker encryption key. Both processes must receive identical OAuth app credentials. Validate real inbox sync, a rich reply, scanned attachments, refresh, revoked consent and retry handling in staging.

### Voice and WhatsApp

Create the ordinary connection first in Channels/Connections. In Calling, configure a Twilio API key/secret and TwiML App SID; set its Voice URL to `<BACKEND_URL>/api/voice-plus/<connectionId>/dial` using POST. Keep the ordinary incoming number URL at `/api/voice/<connectionId>`. All callback URLs are computed from the public `BACKEND_URL` and signatures are checked against that exact origin/path. Use HTTPS and permit microphone access. Enable media authentication in Twilio and verify account settings before retaining recordings.

Only enabled, valid plan/membership/role credentials can place calls. Each browser grant can create one destination-bound call. The server ignores client-supplied destination numbers. Configure forwarding numbers and your own recording notice; recordings remain private to authorized staff. Test actual call setup, no-answer/voicemail, DTMF, notice playback and provider callback ordering with the business account.

For WhatsApp, bind the correct Business Account ID, submit a template and wait for approval. The API never follows a provider-supplied pagination URL; it uses only the opaque cursor with the configured Graph endpoint. Test template parameters/buttons and scanned media with approved recipients.

### SAML / SCIM

Supply `SAML_ENTRY_POINT`, `SAML_IDP_ISSUER`, `SAML_IDP_CERT`, `SAML_SP_KEY`, `SAML_SP_CERT`. Store PEM data securely; literal `\n` escapes are supported. Require both the response and assertion to be signed with SHA-256. Metadata and ACS URLs are workspace-specific:

- Metadata/entity ID/audience: `<BACKEND_URL>/api/sso/saml/<slug>/metadata`
- ACS: `<BACKEND_URL>/api/sso/saml/<slug>/acs`
- Sign-in: `<BACKEND_URL>/api/sso/saml/<slug>/start`

Enable company SSO through Security, then explicitly link an existing identity. Owner-issued SCIM tokens last 90 days; save the one-time display in the IdP and rotate it before expiry. Endpoint: `<BACKEND_URL>/api/scim/<workspaceId>/v2`. Advertised resources are Users only. Provisioning never grants owner/admin roles. Record the IdP persistent subject in `externalId` when SAML linking managed accounts. Test actual IdP integration, MFA, replay rejection, seat exhaustion and deprovisioning before rollout.

### Recurring billing and accounting

Create monthly INR Razorpay plans whose **tax-inclusive per-seat amounts** match `WORKSPACE_PRO_INR_PAISE` / `WORKSPACE_PREMIUM_INR_PAISE` plus the configured tax rate. Set `RAZORPAY_PRO_PLAN_ID` and `RAZORPAY_PREMIUM_PLAN_ID`. Use the existing signed `/api/razorpay/webhook` and subscribe to subscription lifecycle/charged events in addition to payment/refund events. The service fetches current payment, subscription and invoice records; access is tied to the invoice's billing period, not when a delayed webhook happens to arrive. Plan IDs are snapshotted on new subscription requests.

A creation request is durably reserved before the provider call. An unknown result is not automatically retried, preventing a timeout from creating a second mandate. Reconcile the matching subscription ID from your provider dashboard using the UI; the server verifies its stored request-key/workspace notes before binding it. A captured matching paid invoice is still required for access. Handle unusually late/conflicting purchases through accounting reconciliation rather than creating another mandate blindly.

Issuance/credit notes require explicit accounting review. Where applicable, obtain an acknowledgement through your contracted government/GSP workflow first, then record it and export the package. This extension provides records and integration points, not GST filing software. Use test-mode provider fixtures before any real payment.

### Scalable search

Configure a private Qdrant service/API key, `QDRANT_URL`, `QDRANT_COLLECTION`, and the embedding model's `EMBEDDING_DIMENSIONS`. Run `npm run vector:init --prefix backend`, then re-index published knowledge. A collection's dimensions must match its model; use a new collection when changing dimensions. The optional `deploy/compose.vector.yml` overlay uses a caller-supplied pinned `QDRANT_IMAGE`; it exposes no vector port to the host.

Each query/write/delete is tenant-bound. Retrieved rows are checked again against current MongoDB workspace, model and published article hash, so obsolete/draft vectors cannot become sources. Re-index after article changes. Index pruning removes obsolete points for that workspace only. Verify real vector/embedding provider behavior and retrieval quality in staging.

## Operations and backup drill

Set a random `METRICS_TOKEN` of at least 32 characters. Scrape `/api/metrics` with `Authorization: Bearer <token>` over your private/HTTPS monitoring network. It exposes only aggregate readiness and failed-delivery counts. `npm run monitor:helpdesk --prefix backend` checks readiness every minute; optional `MONITOR_WEBHOOK_URL`/`MONITOR_WEBHOOK_SECRET` enable signed aggregate alerts. No alert is sent unless explicitly configured by the operator.

For a reproducible backup, stop API mutations **and** the helpdesk worker during a maintenance window. Set `BACKUP_QUIESCED=1`, `MONGODB_URI`, `PRIVATE_UPLOAD_DIR`, `BACKUP_DIR`, and a strong `BACKUP_PASSPHRASE` through a private shell/secret manager. Install MongoDB Database Tools and `tar`, then run `npm run backup:helpdesk --prefix backend`. The tool captures a compressed MongoDB archive and private files together, encrypts the package with AES-256-GCM using a scrypt-derived key, and publishes it only after completion. It does not pretend to coordinate a live application snapshot automatically.

Keep `INTEGRATION_ENCRYPTION_KEY` separately in the secret manager. To test recovery, decrypt with `node backend/scripts/decryptHelpdeskBackup.mjs <backup.tar.enc> <snapshot.tar>` with the passphrase in the environment, unpack in an isolated location, restore the database archive with MongoDB tools to an **isolated** replica set, restore the private files and original integration key, then exercise login/tickets/downloads. The decrypt tool checks the authentication tag before publishing its output. Do not restore over production until the isolated drill has succeeded and the cutover is explicitly approved. Add offsite copies, retention, access controls and scheduled restore exercises in your hosting environment.

## Verification boundaries

Unit and integration suites cover sanitization, signatures/media formats, tenant vector requests, atomic bulk changes, file visibility/delivery, OAuth refresh and secret redaction, destination-bound calls/replay, provisioning/deactivation, invoice/credit limits, recurring invoice/payment replay, AI acceptance scoring and actual signed SAML validation/tampering/replay. Provider HTTP responses are simulated; no real account call, payment, email or mandate is made.

The browser suite exercises ticket table/bulk actions, formatted replies, advanced setup navigation, customer support and existing responsive/security workflows. Local Chromium cannot start in this workspace due to its socket restriction; GitHub Actions is the browser execution environment. Check that run before merging. A successful fixture suite does not establish live provider, production deployment or full commercial-product parity.

## Browser inbound calls and live transcripts

Calling setup can enable browser inbound routing and Twilio Real-Time Transcriptions (English US/India or Hindi). Both recording and live transcription require a caller notice. Configure the company's Twilio API key/application and public HTTPS callbacks before enabling. Agents select **Receive calls in browser**, allow microphone/audio permissions, and remain online. A 90-second availability lease renews every 30 seconds; only one receiving browser per member is allowed. The incoming-only JWT cannot initiate arbitrary outgoing calls. Routing rechecks membership, custom permissions, seats, session revocation and MFA; active calls exclude the agent from another assignment. IVR labels match manual or SCIM routing groups. Unanswered browser calls use telephone forwarding, then existing voicemail fallback. Provider charges apply.

Signed Twilio callbacks store final transcript segments only; `(call, transcription SID, track, sequence)` deduplicates deliveries. Authorized staff can read a paginated, private transcript endpoint under the ticket call, and the ticket phone panel polls for new content. Track names describe incoming/outgoing audio, not inferred speaker identities. Transcript data is private workspace data and is included in database backup/retention operations. Live transcript generation needs the Twilio transcription product enabled and provider-supported languages. Automated tests verify callback handling, not real PSTN audio.

## SCIM Groups

`/api/scim/:workspaceId/v2/Groups` supports list/read/create/replace/PATCH/delete, equality filters on displayName/externalId, and pagination. Group member `value` references a SCIM **User resource ID**, never a global account or membership ID. PATCH supports add/replace/remove members and `members[value eq "id"]`, plus displayName changes. Limits: 100 groups/workspace, 1,000 unique members/group, 50 patch operations/request. Group labels derive `Membership.scimGroups` for routing; manually configured groups remain unchanged. Groups do not grant roles, seats or permissions. Rename/removal recalculates derived membership in the workspace transaction. User deactivation still excludes staff from routing.

## WhatsApp template media headers

Upload a public scanned attachment to its ticket, then choose it as the approved template header. PNG/JPEG images, PDF documents and MP4 video are supported. The server scopes the file to that ticket/workspace, uploads it to the configured Meta phone number, binds it to the ticket message and queues a media header component. Text and media header parameters are mutually exclusive. The chosen media type must match the template approved by Meta; provider errors appear in the durable outbox. Private notes/files cannot be sent.

## ClearTax e-invoice submission

Accounting includes **GST e-invoice registration**. Owner-only preparation derives a B2B service-invoice government payload from the immutable paid invoice, with explicitly supplied city/PIN data. GSTIN/state, tax totals, SAC and invoice-number format are validated. Amounts convert paise to rupees and basis points to GST percentages. An owner reviews the exact payload and authorizes submission by payload hash and environment. Sandbox acknowledgements are labelled `sandbox-registered`, never production registrations. Configure ClearTax/NIC seller onboarding and the environment variables in `backend/.env.example`; production additionally requires `CLEARTAX_PRODUCTION_ENABLED=true`.

Submission state is persisted **before** network I/O. Timeouts, HTTP errors and malformed acknowledgements remain `outcome-unknown`; they are never automatically retried. Reconcile those invoice numbers in the ClearTax portal. A definitive provider rejection permits a corrected preparation. Government IRN/acknowledgement/QR data is retained privately for the accounting team to use in the existing reviewed-issuance flow. This adapter registers e-invoices; it does **not** file GSTR returns or replace the selected GSP's DSC/EVC/OTP signing workflow. Live return filing still requires choosing/onboarding that service and implementing its contracted API flow.

Provider API references: [Twilio transcription](https://www.twilio.com/docs/voice/twiml/transcription), [ClearTax government-compatible Generate IRN](https://docs.cleartax.in/cleartax-docs/e-invoicing-api/e-invoicing-api-reference/govt-compatible-apis/generate-irn), [ClearTax account setup](https://docs.cleartax.in/cleartax-docs/e-invoicing-api/e-invoicing-api-reference/setting-up-your-account).

## Email-first customer support and server OTP

Email is the primary customer identifier and contact channel; no phone number or WhatsApp account is required. New portal/widget requests create a pending conversation and queue a six-digit OTP. Creation returns only ticket ID/number, random challenge and timing metadata. The server grants conversation access only after verifying the OTP; the browser cannot mark itself verified. Codes expire in 10 minutes and are single-use with five attempts, a 60-second resend cooldown and a durable five-delivery limit per recipient/workspace/hour. Verification storage uses an HMAC tied to workspace, ticket and random challenge; the outbox contains only encrypted OTPs. Keep `JWT_SECRET` and `INTEGRATION_ENCRYPTION_KEY` stable and private. Codes are never returned by customer APIs. Expired/superseded/locked OTP jobs are skipped.

A customer can recover a conversation from the emailed ticket link by entering its email and requesting a new OTP. Successful verification rotates the conversation access token. Existing browser sessions may consequently need to verify again. Previously issued staff email links remain valid during transition; pending conversations are otherwise inaccessible until verification.

New portal requests automatically bind to the oldest enabled email connection in that company. After OTP verification, public agent replies use its email outbox; incoming mailbox replies with the `[QF-...]` subject thread to the same ticket only when the sender matches the contact. Configure the existing IMAP/OAuth or signed inbound-email integration for real two-way email. With no email connection, agent replies use the application SMTP notification outbox and link to the OTP-protected portal; incoming replies to that SMTP address require a separately configured mailbox/gateway. Internal notes never generate customer emails.

Configure the sending mailbox or `EMAIL_USER`, `EMAIL_PASS`, `SMTP_HOST`, `SMTP_PORT`, and run `npm run worker:helpdesk` before live use. OTP jobs and reply jobs use the durable retry queue and surface delivery failures in the workspace outbox. Automated tests use a mailer fixture; live email delivery still requires a real SMTP/OAuth mailbox and deliverability checks.

Phone/WhatsApp are optional integrations. The global browser phone is hidden unless an administrator enables browser inbound calling; phone actions appear on phone conversations. WhatsApp template/media actions appear on WhatsApp conversations. Email verification and support work without either provider.
